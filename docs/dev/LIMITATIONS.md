# Limitations, Non-Goals & Deferred

The honest v1 limits of the shipped binary, stated plainly. None of these are
hidden in the other docs; this collects them. Vultrino is **alpha** (`0.1.0`).

## v1 limitations (real, in the code today)

- **Only the file storage backend is implemented.** `[storage] backend =
  "keychain"` and `"vault"` parse but error at runtime ("not yet implemented").
  The encrypted file vault is the only working backend.
- **Streamed metering has honest residuals.** A `{"stream": true}` LLM call is now
  forwarded as incremental SSE with a streamed token meter (V13b), but: a capability
  whose `(credential, action)` matches an operator `block`/`redact_patterns` egress
  rule is served **buffered** (the incremental scrubber runs only the always-on
  literal credential-secret scrub, not arbitrary whole-body regex/block); a
  residual-compressed response is withheld at the streamed head before any body
  byte is released. A streamed call that ends without the provider's usage
  trailer (client hung up and the drain hit a cap, a truncated or halted stream, an
  NVIDIA tool stream) is charged an **estimate** marked `dims.estimated = "true"`,
  not the provider's exact count: about one token per three generated bytes, capped by
  the request's own output limit, and rounded up on purpose. It can still come out LOW:
  hidden reasoning tokens are not in the stream, text carried outside the `delta` keys
  is not counted, and a provider that reports cumulative usage on every chunk is read as
  complete on its first chunk. The estimate needs a
  request model to price with; a stream with no model meters the V13a `api-calls=1`
  event only. See [METERING.md](METERING.md).
- **The priced-model gate covers the LLM proxy only, and trusts the request's model.**
  `[llm_proxy] require_priced_model` (default on) refuses an `/llm` request whose model the
  rate card does not price, before the upstream call. It does not gate a model call made
  through `POST /api/v1/execute`, an MCP `http.request` or a named tool: those are metered
  (the event carries whatever model the body names) but an unpriced model there is still
  rejected by leria as unpriced and books $0, so budgeted agents should reach models through
  `/llm` only (the capability and policy for the credential decide that). The gate reads the
  model the upstream URL selects where the URL picks it (Gemini and Vertex `models/<id>`,
  Bedrock `model/<id>`, Azure `deployments/<name>` through `[llm_proxy.azure_deployments]`; a
  deployment not in the map is refused), else the body's `model`; a body model that differs
  from the URL's is refused. It cannot know which model the provider really bills if it
  serves a different one: the token event is booked under the served model, priced or not
  (the requested id stands in only for a dated form of it), so an unpriced served model is
  counted by leria as unpriced and holds its watermark rather than being booked at another
  model's price, but that call has already been made. Unknown request
  features are refused: the proxy admits only the top-level request fields, `anthropic-beta`
  values and plain client tool shapes it knows bill tokens alone (a per-protocol allowlist in
  the code), and answers `403 modifier_unpriced` to anything else, including compaction,
  `context_management`, `fallbacks`, fast mode, `inference_geo`, any service tier in any
  casing, search options and server tools. Operators widen the allowlist only by a code change
  (the rate card has no entry for a priced variant); a pricing decision, not a setting. The
  contents of an allowed field are not inspected, except the media and modality markers (a
  Gemini `inlineData` or `fileData` part is admitted only for image, PDF or text media types,
  found at any depth in any object or array shape; `responseModalities` must be exactly
  `TEXT`; an OpenAI content part must be text or an image, and a `data:` image URL must declare a priced media type), which are refused otherwise; the declared media type is what is checked: inline bytes and provider-fetched URLs (http(s), `gs://`, Files API, YouTube `fileUri`) are not inspected, and the `output` arrays of `function_call_output` and `custom_tool_call_output` items are not scanned; an OpenAI `file` or `input_file` part (a PDF included) is refused until allowlisted, so a PDF part passes only on Gemini; an entry with no type is admitted and only its content parts are checked; other nested options stay uninspected, and the regional-endpoint premium of a Vertex
  or Bedrock deployment is booked at the base price (an under-count). Every entry of
  `usage.iterations` is counted (the larger of the top-level figure and the sum of the entries,
  per direction), at the request model's price. Server-tool fees are refused, not metered. The card is
  read from a file and a change can only NARROW coverage: vultrino serves the intersection
  of the card it read at start and the latest good file until it restarts, because leria
  reads the file only at start (so a model added to the file after leria started is refused
  here and a model removed is refused at once). The posture `rate_card.sha256` is the start
  card's fingerprint and `file_sha256` is the file now; `verify-posture` compares `sha256`
  with leria's, and vultrino does not compare it itself. Vultrino's parser refuses what
  leria's refuses (unknown fields, a missing or repeated `rate_card_version`, a one-sided
  input or output price) and is stricter where they differ. Cache tokens are booked as input
  tokens: a cache read at 1x (an over-count, the provider bills about 0.1x) and a cache write
  at 2x (never below the provider's 1.25x or 2x, an over-count for the 5-minute cache).
- **The meter emit is fail-open / out-of-band.** A failed `append_event` still does
  not fail the action it describes, and it mints no sequence, so the stored stream
  stays contiguous. It is no longer silent: every failed append is counted (reported
  on `/api/v1/health`, `/api/v1/ready` and `/api/v1/posture`) and the next
  successful append is followed by a `meter.lost` marker event with the count, the
  first and last failure times and the lost event types. While appends are still
  failing, `GET /api/v1/events` reports the pending count as `meter_gap_pending` so a
  poller can freeze its freshness watermark during the outage; govder reads it to pause
  agents with a spend cap (the control is govder's meter-stale Deny, not vultrino). The
  calls themselves are still admitted by vultrino (a full disk does not fail closed on the
  gateway), so with no govder watching, metered calls stay unmetered for the whole outage. The count is
  held in memory:
  if the process dies before an append succeeds again the marker is never written,
  and the consumer's stale-watermark detection is the only remaining signal. An
  out-of-band meter still bounds, but does not eliminate, overshoot. (See METERING.md
  "Honest bounds".)
- **No cumulative spend / budget state.** SpendCap is **per-action and stateless**
  only — there is no ledger. Windowed budgets are a metering-plane concern returned
  as a pushed `Deny` policy.
- **Vault writes append one record; a compaction still rewrites the whole vault.**
  Since format v10 a write (a policy PUT or delete, a credential, role, API-key or
  use-token change, an approval decision) takes the cross-process file lock,
  catches up on the log records other processes appended, applies the change and
  appends ONE encrypted record holding only the records it changed, then fsyncs it.
  The bytes written and the decrypt work of a write do not grow with the vault
  (counted by `cargo run --release --example vault_cost`, not timed). Bounds that
  remain: when the log grows past the larger of 256 KiB and the snapshot size, the
  write that crosses it also rewrites the whole snapshot (amortised constant, but
  that one write is O(vault)); opening the vault decrypts the snapshot and replays
  the log (at most about twice the snapshot); in-memory shape validation and the
  kill-fence diff still walk the in-memory records on every write; the signed
  outbox is a separate file that its own store still rewrites whole; and writes
  are still serialised by the one lock. A newline-terminated log line that fails
  to authenticate fails the open closed instead of being skipped: an operator must
  inspect the log (a torn, unterminated final line from a crash is ignored and
  truncated by the next writer). Latency on native arm64 and on the amd64 VPS has
  not been measured by this change.
- **Policy propagation across processes is bounded-staleness, not instant.** An
  admin policy push is synchronous on the web process but reaches the MCP server /
  other replicas only on the periodic refresh (`POLICY_REFRESH_SECS = 5`). For an
  immediate kill, revoke the use token (storage-authoritative). Kill policies are
  additionally fenced from the vault before every dispatch (P3-KILL), so they do not
  wait for the refresh; ordinary Deny policies do, and `VULTRINO_POLICY_REFRESH_SECS`
  (1 to 86400) stretches that wait up to a day.
- **Kill fence: one-way vault format and a mixed-build window.** The fence stores its
  epoch in the vault (since `STORAGE_VERSION` 9, now 10); an older binary refuses a
  newer vault, so the first start of this build backs the vault up (see below).
  Stop every vultrino process sharing the vault before starting the fence build: an
  older process already running is not fenced and can still dispatch after govder
  reports Contained (the model's `KillFence_mixed_builds` counterexample), most
  plainly on lock-free `vk_` API-key and LLM-proxy calls. A v9 process that rewrites
  the vault under a running v10 process is detected at the v10 process's next
  vault read and refused (fail closed), but only after the v9 process has written.
- **Vault format v10 is one-way, with a backup.** The first open of a v9 or older
  vault copies the vault file to `<vault>.v9.bak` (the version it found; atomic,
  owner-only; an existing backup is never overwritten: if it differs, the copy goes
  to `<vault>.v9.<unix-nanos>.bak`) and rewrites it as a snapshot plus an empty log.
  The file names replace the extension of the vault file: for `credentials.enc` they
  are `credentials.wal` and `credentials.v9.bak`. To roll back: stop every process,
  delete `credentials.wal`, restore `credentials.v9.bak` over `credentials.enc` and
  start the v9 build; every write made after the migration is lost. If the log is
  left behind, the next open of the restored v9 file refuses to start (a log beside a
  pre-v10 snapshot is never replayed) and names the file to delete. A backup of a v10
  vault must copy the vault file and its `.wal` together, with the processes stopped
  (or under the lock). The `.wal` is part of the vault, not a cache: a vault file
  restored without its `.wal` is refused at open (every v10 vault has one, empty
  after a compaction), and restoring a `.wal` from a different moment than the vault
  file fails the open or silently drops the records written in between, including a
  kill. A running process refuses (every dispatch fence read and every write fails
  closed) if the `.wal` is removed or shortened while the snapshot is unchanged. The
  refusal is per process and not permanent: a process started after the shrink opens
  the shorter log, and a later compaction or foreign append makes a refusing process
  reload and accept the shorter state. If the vault file itself is deleted under a
  running process that has already loaded it, the process refuses the same way: every
  fence read and write fails closed and keeps failing while the file stays gone,
  including right after a compaction when the log is empty too, and a write does not
  recreate the file. The refusal ends when a vault file reappears: a restored file is
  reloaded and accepted (an older copy is accepted as the older state), and so is any
  file that decrypts under the process's key. A fresh vault created by a new process
  has a new salt, so the refusing process keeps failing with a decryption error while
  the new process starts clear, as for any vault that never existed. A missing `.wal` has one benign
  cause: a vault created by an earlier build that crashed between the snapshot rename
  and the log creation, which needs an empty file at that path and not a restore. The checks cannot notice the same edit made while no process is running
  (a truncated log whose remaining records still parse opens as the shorter state;
  offline `.wal` tail truncation without a durable anchor is an accepted limitation,
  because filesystem write access is outside the threat model),
  and they do not defend against an attacker who can write the vault directory:
  such an attacker can also put back an older copy of the vault. Use `vultrino vault backup <dir>`
  and `vultrino vault restore <dir>` rather than copying files by hand (the Solo VPS
  nightly backup does): backup holds the exclusive vault lock while it copies the
  snapshot, the `.wal`, the outbox and the averin stores together with a SHA-256
  manifest, then checks the copy; restore verifies the manifest, every checksum and an
  open of the copy before touching the target, refuses a backup without the snapshot
  or the `.wal`, replaces an existing vault only with `--force` (moving the old
  files aside), and leaves `<vault>.restore-pending` if interrupted, which stops the
  vault opening until the restore is re-run. Stop the service before a restore: a
  non-durable service holds the vault lock only per operation, so restore does not
  detect it (backup is safe under a running non-durable service, it pauses
  dispatches for the copy; the durable averin queue refuses both). They do not detect
  a rollback to an older but self-consistent backup, and restoring an older backup
  silently undoes every kill, revocation and approval made after it: before starting
  the service the operator must re-apply the kills and revocations made after the
  backup time and check Govder's kill state. A backup is refused while
  `<vault>.restore-pending` exists. A damaged final `.wal` line
  stops startup; `vultrino vault check` says whether removing exactly that one
  record makes the vault open, and `--truncate-final` cuts it (kept in a side file;
  the cut record is a lost mutation, so redo a kill or revocation that was in it).
  Damage anywhere else is refused, not guessed at.
- **Vault change detection and lock behaviour.** Another process's commit is noticed
  through the snapshot's (mtime, length, inode) token plus the log length; a
  filesystem with coarse timestamps is unsupported (this now covers writes and the
  fence, not only the read cache). A waiting writer holds the
  sidecar `<vault>.gate` file exclusively while it waits for the vault lock, and every
  shared reader passes through that gate before taking the vault lock, so new fence
  reads queue behind a waiting kill write instead of starving it. Readers hold
  the gate for a few syscalls, so a writer gets it quickly in practice, but `flock`
  gives no writer preference on the gate itself, so that is observed, not a bound
  (a probe with 32 looping readers saw kill writes wait 11 to 29 ms; the test uses
  eight looping readers). It relies on `flock` semantics on a local filesystem (not
  NFS, FUSE or Windows). Writers still serialise one at a time on the gate. In-process lock-free readers (`get`, `get_by_alias`,
  `get_policy`, the fence epoch) block for one log fsync per write and for a
  whole-snapshot encrypt and fsync on the write that triggers compaction; a fence
  catch-up after a foreign write validates and re-indexes the whole vault under the
  in-process cache lock (O(vault) CPU, no decrypt beyond the new records). A failed
  append is taken back out of the log on a best-effort basis; if that also fails the
  line may be read as committed.
- **Kill fence cost.** Every dispatch, including `vk_` and streamed LLM-proxy calls that
  were lock-free before, takes the cross-process vault lock SHARED and reads only the
  log records appended since the process last looked: an unchanged vault costs two
  stats and no decrypt, and dispatches do not serialise against each other, only
  against a writer. A burst of writes by other processes makes the next fence read
  decrypt those records (and rebuild the in-memory indexes). Latency is not measured.
- **Kill marks are keyed by policy id.** Re-storing a kill policy id with a narrower
  or retargeted pattern overwrites its mark, so work admitted before the original kill
  and no longer matched can run after a later lift. govder's ids are per-target; an
  admin-edited kill policy is not covered.
- **Kill marks are garbage-collected by a bounded rule.** The periodic vault GC drops
  a mark only when its kill policy is no longer stored as a kill, the mark is at
  least 24 hours old, and no approval that can still be claimed was admitted at an
  epoch below the mark's (an approval with no recorded epoch counts as 0). The
  epoch is never lowered. Marks from before v10 are stamped at migration and age out
  24 hours after it; a mark with no timestamp is never collected. The 24 hour grace
  is the only protection for a live call in flight inside one process (its admission
  epoch is in memory only): a request that stalls for more than 24 hours between
  admission and dispatch could run after its mark was collected.
  The grace compares the storing process's wall clock with the collecting process's
  wall clock, so a clock that steps forward, or a host that was behind when the kill
  was stored, shortens the effective grace. The govder TLA+ model
  `formal/tla/KillFence.tla` models the fence as an epoch comparison that is never
  collected (it has no marks and no collection), so its `NoStaleDispatch` property
  does not cover a collected mark.
- **A fence read that catches up after a foreign write still revalidates the whole
  vault in memory.** It decrypts only the new records, but runs shape validation and
  index rebuild over every record while holding the in-process cache write lock. In a
  web plus MCP deployment where every dispatch writes a use token, most fence reads
  in the other process pay this. The vault cost counters count decrypts only.
- **At-most-once execution sacrifices automatic recovery after an ambiguous
  crash.** Reserve → operate → complete are not one external transaction. If a
  worker disappears after claiming an approved action, a stale claim is finalized
  as `outcome unknown` and is never run automatically again. A human must inspect
  the target and explicitly re-approve if retry is appropriate.
- **Legacy approved records without sign-off evidence fail closed on upgrade.**
  Vault load now revalidates approval shapes before exposing any record. A pre-V12
  `Approved` entry with an empty `signoffs` array is indistinguishable from a vault
  edit that forged the status byte, so Vultrino refuses to open that vault rather
  than execute it. Resolve or export such pending legacy approvals with the prior
  binary before upgrading; denied, expired, pending, and evidence-bearing records
  remain readable when their stored lifecycle fields are internally consistent.
- **Vault shape validation proves consistency, not provenance.** The authenticated
  vault ciphertext detects edits by a party without the vault key, and the loader
  plus execution witness reject impossible or unsatisfied approval shapes. A party
  that already controls the vault encryption key can still create a new,
  internally consistent ciphertext containing fabricated sign-off identities;
  preventing that requires independently signed decision evidence and belongs to
  the cross-plane Govder/Averin composition proof.
- **Egress scrubbing is defense-in-depth, not absolute (byte-exact match against
  derived forms).** It scrubs the credential's own secret and the common *single-pass*
  encoder dialects an upstream might ACCIDENTALLY reflect it through: raw, percent-encoding
  (full, both hex cases + form-url `+`-for-space + the common library DEFAULT safe-sets — JS
  `encodeURIComponent`'s `!~*'()`, Python `urllib.parse.quote`'s `/`, Go `url.PathEscape`'s
  `$&+=:@` and the RFC 3986 `pchar` set `!$&'()*+,;=:@`), base64 (standard and URL alphabet,
  padded and unpadded) and hex (both cases) of the WHOLE value, the whole-group base64 cores of the
  value for each of the three alignments it can have inside a longer base64 string (so the base64 of
  `Bearer <token>` is scrubbed, apart from the 0 to 2 bytes beside the core, and only when the core is
  at least 16 characters), JSON string escaping
  (`\"`/`\\`/control), slash-escaping (`\/`), ensure_ascii `\uXXXX` (both hex cases), and
  HTML-safe `</3e/26`, composed where realistic. This catches a buggy upstream echoing the request. It does NOT
  defend against an **adversarially-encoding** upstream: byte-exact matching cannot beat
  arbitrary re-encoding (hashing, an encoding other than base64 of the value inside a longer
  string, a value split across separate SSE events, chunk-reordering,
  a novel escape dialect). The
  real protections there are that vultrino never trusts the upstream beyond the injected
  credential, the **buffered-block fallback** for unparseable/compressed bodies, and an
  operator `block`/`redact_patterns` rule. Secrets shorter than `MIN_REDACT_LEN = 5`
  force buffered execution and content-free whole-response withholding. Buffered
  and streamed output receive a final exact-form check after replacement; the
  streamed check includes the preceding released suffix, so neither the redaction
  marker nor a chunk boundary can reconstruct a declared form. A structural fix
  (decode-then-match normalization) is a deferred follow-up.
- **Halt abort callbacks are per-process.** The in-flight session registry is
  in-memory per process, so leg 3 of a halt (firing abort callbacks) only preempts
  in-flight work *in the process that received the halt*. The cross-process
  guarantee is "deny the next gated call" (token revoke + kill policy), which is
  immediate.
- **Plugin hot-reload is limited.** The `web` server scans plugins from disk
  **once at startup**; a plugin installed via the CLI while `web` is running is not
  picked up until restart. `vultrino plugin reload` validates a plugin but does not
  hot-swap it into a running server.
- **WASM ABI v2 has no secret-using host capabilities yet.** An untrusted guest
  receives only a non-secret credential handle (alias + type), and ABI v1 modules
  are rejected at installation/loading. Consequently, external WASM actions that
  need private key or token bytes are unavailable until Vultrino provides a
  narrow host-side operation for that credential type. The repository's former
  PGP module is retained only as an ABI v1 rejection fixture, not a deployable
  plugin.
- **Inbound workload identity: Vultrino does not verify the SVID/OIDC token itself.**
  The edge verifies the token; Vultrino verifies the edge's signature over the
  document (`<header>-signature`, HMAC under `VULTRINO_IDENTITY_SECRET`, bound to the
  request's bearer secret and a five-minute expiry). Whoever holds that key can
  assert any workload id, so it is as sensitive as the approval-assertion key.
- **In-memory, per-process state resets on restart.** Rate-limit counters, the
  unauthorized-attempt metric, and the in-flight session registry are per-process
  and reset on restart. The durable history is the signed outbox. Rate-limit
  counters are keyed per `(rule, credential, principal)` — distinct caps and
  distinct principals each get their own counter (so two agents sharing a
  credential no longer drain one shared budget).
- **A `RateLimit` nested under `or` or `not` is not part of the layered guard set.**
  Layered Allow-`RateLimit` rules are conjunctive: every matching Allow rule's
  top-level `RateLimit` (a bare rule, or inside `and`, at any `and` depth) joins one
  guard set per request, the request is admitted only if all of them have room, and
  then all are charged together under one lock (a refused request charges none). A
  `RateLimit` written inside `or` or `not` keeps the old inline evaluation, because
  "all caps must pass" has no meaning there. The compiled shapes (a bare rule, or
  `and` of an action match and limits) are all covered. A `RateLimit` under `or`/`not` is
  charged on EVERY request that evaluates it, refused ones included (an over-charge, fail
  closed), unlike the layered set, which charges only admitted requests. An unlimited Allow rule that also
  matches the request (in the same or another matching policy) does not switch a matching
  limit off: the limits apply to the request whichever Allow rule matched, so a broad
  allow-all policy on a credential no longer lets an exhausted rate limit through. Which
  matching rule's reason is reported still follows policy storage order.
- **No built-in TLS / network hardening.** The server speaks plaintext HTTP;
  terminate TLS at a reverse proxy and bind to localhost unless fronted.
- **Audit-to-file is not implemented.** `[logging] audit_file` is parsed but unused;
  the web "audit log" page is a TODO. Admin mutations are logged via structured
  `tracing`; the durable event history is the signed outbox.
- **Durable-queue compaction and delivered-prefix pruning are best-effort GC that
  run on the periodic tick and yield to in-flight commits.** They wait up to
  `COMMITTING_DRAIN_TIMEOUT` (5s) for the `committing` set to drain, and skip the
  tick if it doesn't. Under sustained append saturation (the committing set never
  fully empties within the window) they skip every tick, so journal segments and
  delivered records' raw params can grow and are retained past the retention
  window until append traffic quiesces. Each skipped tick is logged at `warn`
  (target `averin_seal`) so the condition is observable. This is a deliberate
  bound: the queue never blocks the GC/delivery worker and never risks losing or
  resurrecting an in-flight event — it defers reclamation until a lull. Averin
  durable sealing is default-OFF.

- **Workload-exchange token multiplication is BOUNDED, not eliminated: the honest
  invariant is ≤2 live generations DURING ROTATION, not "exactly one".** Predecessor-retire
  (mint-then-retire, expired-token-skipping, one bulk `locked_mutate` pass) is the primary
  control, and it is deliberately **best effort**: if the retire fails, the exchange still
  returns the credential it already stored, because failing there would hand a retrying
  workload an error for a mint that succeeded — which produces *more* generations, the
  opposite of the goal. The failure is logged at `warn` and backstopped by
  `max_live_generations` (grant-declared; `None` means the default **4**, never
  "unbounded"), which **refuses** the next exchange once that many live, unrevoked,
  unexpired generations exist. That refusal is fail-closed and self-healing: expired
  tokens do not count, so the cap clears within one TTL. Steady state is 1; the default
  leaves headroom for a pod restarting while its predecessor is still unexpired.
  Why the bound exists at all, measured: an unbounded live set grows **linearly in
  uptime** (`revoked_tokens: 38` after 19 minutes at a 60s refresh, ~1,150 tokens/day/agent
  at a realistic L3 TTL), and grant-delete revoke is one full-vault rewrite per token
  (4.6s at 120 tokens, 20.8s at 240) against govder's 10s enforce-client timeout — so past
  roughly 150–200 accumulated tokens the **W2 containment leg stops completing inside its
  own budget.** A sidecar restart cap is an availability guard, never a security bound: the
  multiplier is workload-controlled and unthrottled (120 exchanges in 22.4s measured), and
  jti replay protection forbids replay, not fresh minting.
- **The rate-limit counter now keys on the agent, not the token — which is a change of
  meaning, not just a fix.** It previously charged `principal_id`, which for a use token is
  the token id, so every rotation minted a fresh counter and a compiled cap reset per
  generation (measured: 6 requests in ~1s under a 2-per-hour cap). The doc comment already
  stated per-agent isolation as the intent. It is now keyed on `agent_label` with an id
  fallback, so a rotating workload shares one window. The **per-process, per-replica** bound
  below still applies on top of it.
- **Workload-verifier shape is checked at startup, but signer alignment is still an operator
  obligation.** When workload exchange is enabled, `vultrino web` refuses an absent, blank,
  unreadable, or <32-byte verifier before vault access or listener bind. A comma-separated
  overlap list is accepted (every entry trimmed and ≥32 bytes; a match against any entry
  verifies), validated once, and frozen in `AppState`. This proves the running process has a
  stable verifier snapshot; it cannot prove that the external identity-edge signer holds the
  matching key. A validly shaped but mismatched key therefore starts successfully and rejects
  every assertion with `401 invalid_workload_identity`.
- **Policy-hash presence is checked at startup, but stability across restarts is still an
  operator obligation.** `VULTRINO_POLICY_HASH_SECRET` remains env-only; putting it in
  `config.toml` looks plausible but does nothing because unknown TOML keys are ignored.
  Production `vultrino web` refuses an unset/blank value before touching the vault. It cannot
  prove cross-process key continuity: rotating the value makes every previously authored hash
  mismatch, i.e. false drift. The reusable embedded/test constructor remains permissive and
  emits an empty hash when no key is supplied; it never falls back to a bare digest.
- **There is no per-policy rules read-back.** `GET /api/v1/policies/{id}` does not exist and
  the collection GET returns a reduced DTO with no rules, so an external verifier cannot
  read back what a policy actually enforces. It can only compare `content_hash` (see above)
  and assert on the grant set the decide plane reports. Any claim of the form "we verified
  the compiled rules" is really "we verified the hash and the grant set".
- **A credential minted by a plugin that then returns an error is neither persisted nor
  scrubbed.** Scrubbing of material minted or refreshed during an action (OAuth2 refresh,
  Google service-account mint) works from the plugin's successful response. If a plugin
  mints a token and then returns `Err`, the minted credential is not stored and is not added
  to the scrub set for that call's error text. The built-in plugins do not echo a minted
  token in their errors, but a third-party or WASM plugin that did would not be covered.
  Closing this needs a plugin API change so an error can carry the minted credential; that is
  not done.

- **Policy load ordering is per process.** Every engine policy load (the periodic refresh
  and the admin reload) runs as one cycle under a single async lock, ticketed in list order,
  so within one process an older list cannot replace a newer one. The lock does not span
  processes: a kill policy written by another process (CLI halt, HA replica) becomes visible
  here on the next refresh tick, so propagation stays bounded by the refresh interval.
- **`internal_http` refuses only two named metadata addresses inside its allowed ranges.**
  100.100.100.200 (inside CGNAT) and fd00:ec2::254 (inside fc00::/7) are excluded, including
  IPv4-mapped forms. Another provider's metadata address inside RFC1918, CGNAT or
  unique-local space would still be admitted, because those ranges are allowed on purpose.
- **A client-sent `x-goog-user-project` is dropped on `/llm`, and a gateway-owned Google
  project setting is not offered yet.** The header picks the Google quota and billing
  project on Vertex AI and Gemini channels (including their OpenAI-compatible routes), so
  Vultrino no longer forwards the client's value: the request uses the key's own project,
  the same as an unset gateway setting. An operator who needs a specific project on a
  multi-project key has no credential setting for it today. The drop is on `/llm` only;
  `POST /api/v1/execute` and the MCP `http_request` tool pass the caller's headers through
  as before for this one.

## Formal verification bounds (what the gates prove — and do not)

Stage-1 artefacts under `formal/` are CI-gated on `main` (Lean + nanoda, Kani,
refinement check). They prove **finite modeled invariants under stated TCB
assumptions**, not the whole product and not information-theoretic
noninterference. Honest scope:

- **Lean (`formal/lean/`)** models critical approval / credential-confinement /
  startup / method-authority boundaries and rechecks declarations with the
  independent nanoda kernel (`sorryAx` forbidden). Theorems are universal over
  modeled traces; they are **not** a complete semantic refinement of the async
  Rust server (see `formal/lean/README.md`).
- **Kani (`formal/run-kani.sh`)** runs pure-kernel harnesses with
  `--no-default-features` (no `wasm-plugins` / wasmtime). Kani 0.67 ships rustc
  **1.93** nightly; the production default feature set pulls wasmtime **47**,
  which declares rust-version **1.95**. So Kani does **not** verify the WASM
  plugin host, and a default-features build is outside that proof job.
- **Permit kernel (`src/formal_kernel.rs`, VUL-05).** A direct permit is minted
  only from an `AdmissionWitness` that the pure admission gate builds from the
  policy engine's `Evaluation` of the request, and an approved permit only from
  the re-derived `Granted` witness plus the resume `Evaluation`. `authorize`
  recomputes the approval or request id, epoch, tenant, principal, credential
  alias, canonical action and params digest from the payload and refuses a
  mismatch. Bounds: the kernel trusts its inputs (which policy matched, whether
  observe mode applies, whether approval is required, and that the canonical
  action the server resolved belongs to the label the policy judged); the rule
  digest is not recomputed from the payload; `run_action` unpacks the payload
  after `authorize`, and that code is outside the kernel; `authorize` does not
  check payload fields outside the binding (the credential record beyond its
  alias, the use token id, the evidence subject and action, and whether Averin
  evidence is required); the params digest is over serde_json bytes of the
  stored value, not over bytes an approver saw. The production-binding tests call
  the mint and authorize functions with hand-built payloads; only the integration
  tests drive `prepare_execution` and `resume_approved`. A four-plane end-to-end
  acceptance run for VUL-05 has not been done against this change. govder's
  `e2e-four-plane` CI job checks out vultrino `main` and runs weekly or on manual
  dispatch, so its first armed run after this change reaches `main` counts as that
  acceptance run if it passes.
- **argon2 0.6 port (`argon2-kdf-known-answer`).** The known-answer fixtures were
  generated by this repository's own argon2 0.5.3 build; they are not the
  published Argon2 vectors and not a check against another implementation. Three
  fixed cases and two vault files are tested, not every password, salt or cost.
  Salts shorter than 8 bytes are rejected by argon2 and are not exercised; salts
  longer than 48 bytes were rejected by 0.5.3 and are accepted by 0.6 (vultrino
  generates 16-byte salts, so no existing vault carries one). Admin passwords
  (bcrypt) and API keys (SHA-256) are outside the claim.
- **Refinement (`formal/check-refinement.sh`)** is a source-shape / choke-point
  gate (execution-binding fields, permit mint sites, WASM ABI-before-copy
  install order, pinned harness inventory, etc.). It catches drift of the
  modeled seams; it does not prove the surrounding I/O, networking, or plugin
  implementations correct.
- **Operator-authored truth stays outside the model.** A truthful
  reversible/irreversible label, a correct Govder recipe, and a matching
  workload-assertion signing key are operational assumptions. The gates check
  enforcement continuity of what the stores and verifiers report only in the
  Lean model and as source shape (see above); they do not show that the external
  world matches those labels.

`./ci-local.sh` runs Lean + refinement + the Rust gates; it does **not** run
Kani (install + toolchain cost). CI's separate `kani` job is the authoritative
Kani gate — run `bash formal/run-kani.sh` locally when touching the harnessed
kernels.

## Documented-not-enforced / posture notes

- **LLM credentials are `/llm`-only, by credential, not by provider.** A credential that
  an LLM-proxy capability references is refused on `/api/v1/execute`, MCP `http_request`
  and named tools. The marker is the capability's `credential_ref`, matched by credential
  identity (an alias or a vault id naming the same credential both match); a
  `credential_ref` that names no existing credential is matched by spelling only. A
  second credential holding the same provider key that no LLM capability references is an ordinary
  credential and is not recognised as an LLM channel. Deleting the capability makes its
  credential ordinary again. The check reads the capability catalog on every generic
  dispatch (one extra catalog read, plus one credential lookup per LLM capability, per
  call). Approval resume refuses an LLM credential unconditionally, because the approval
  record does not say which channel opened it; an approval opened on such a credential
  through `execute` before this rule existed does not resume and must be re-requested
  through `/llm`.

- **Reversibility truth remains operator authority.** Production `vultrino web`
  forces strict catalog posture: a catalog outage or missing exact declaration is
  refused, a presented label cannot borrow a canonical sibling, a request cannot
  borrow another credential's declaration, and a shared bare canonical verb cannot
  dispatch directly. Thus every production-web direct path has an exact stored
  `reversible` declaration for the executing credential and action. Approval resume
  also refuses if that catalog authority class changed since open. Production strict
  approval-open refuses an inconclusive Govder recipe answer even for a reversible
  action, and resume requires the exact authority class, normalized recipe, and
  Govder risk facts frozen at open. The parser/library default remains
  non-strict for compatibility with older stdio/embedded callers (new `vultrino
  init` files opt in); those callers must set
  `require_declared_capabilities = true` for the same guarantee. Lean proves
  decision tables about a hand-written model of that rule (the declared class plus
  recipe authority and their open-to-resume continuity), and the refinement gate
  (`formal/check-refinement.sh`) is a structural source-shape check that the code
  still has the expected seams; neither proves the production code enforces the rule
  end to end, which is covered by integration tests. They cannot establish that an operator
  truthfully labeled the real-world side effect reversible, that Govder's stored
  recipe is organizationally correct, or detect an external semantic change not
  reflected in either authority store; those remain explicit operational assumptions.
- **Observe mode is a deliberate downgrade.** A tenant in `observe` mode lets
  ordinary policy denials through (logged + emitted as `policy.observed_denial`).
  Security/financial boundaries (halt, cross-tenant isolation, SpendCap/RateLimit)
  still enforce — but operators must understand observe mode is non-blocking for
  ordinary denials. Separately, `[averin] mode = "observe"` stays fail-open for
  reversible and undeclared work: a missing or failed use seal does not block
  dispatch. **Every receipt that does not reach Averin is recorded individually,
  not only counted**: a failed or timed-out seal, a saturated async fan-out, oversize
  params, a failed local durable enqueue, a durable receipt that exhausted its delivery
  attempts and a lost seal task each become one `evidence.receipt_gap` event on the signed
  outbox (subject = the use token id; payload = token id, project, request id, use
  sequence number, one of `seal_failed`, `seal_task_lost`, `fanout_saturated`,
  `params_oversize`, `enqueue_failed`, `durable_dead_lettered`, a clipped error text, and
  `outcome: action_ran_without_receipt`; never params). The counters
  `receipt_gaps` and `receipt_gaps_overflowed` are on `GET /api/v1/metrics`
  (`averin_seal`). The record is queued in memory and appended to the outbox every two
  seconds: a process killed inside that window loses the gaps it had not yet appended (and
  the counters), and a sustained outbox write failure beyond 4096 pending gaps is counted in
  `receipt_gaps_overflowed` but not recorded individually. A process that dies between the
  action and the enqueue of its seal leaves neither a receipt nor a gap. A gap names an action
  that ran without a receipt; it does not say whether the action's own side effect succeeded.
  **The gap event is not a permanent record on vultrino's side.** The outbox prunes a delivered
  event older than `[outbox] retention_secs` (default **2 days**), and the oldest events beyond
  `[outbox] max_retained_events` whether or not delivered, so a gap survives the shorter of the
  two windows (about an hour at the default cap on a busy host) and an undelivered gap beyond the
  cap is dropped; a gap nobody consumed in that window is gone. The consumer is govder: it receives the signed push on its
  approval webhook, stores each gap (in Postgres when configured, otherwise in memory) before it
  acknowledges the delivery, and lists them per tenant on `GET /v1/evidence/receipt-gaps`. If
  govder is down or unreachable for longer than the shorter of those windows, or has no push target
  configured, the gaps in that window are lost. leria ignores the event type; nothing pages anyone
  about a gap. See govder `docs/dev/API.md`.
  A declared human-floor capability, or a bare canonical verb shared by configured
  business labels, does **not** inherit that availability knob: buffered and
  streaming dispatch require a live Averin client, a bound use token, grant
  material, and a committed use seal before `plugin.execute*`, independent of the
  ordinary Observe/RequireEvidence posture. Unknown `[averin] mode` values are
  refused at config load rather than coerced into Observe, and so is an `[averin]` block with
  `enabled = true` and an empty `resource_id`, or a `base_url` that is empty, does not parse, or is plain
  `http://` to a public address (the same refusals the seal client applies when it is built; it used
  to start with the seal client silently off, so no receipt and no gap event). The server
  constructor refuses too if the client still cannot be built (`VultrinoServer::try_new`; the
  binary reports it as a startup error). A block that parses and builds but names an unreachable
  averin, or a key averin rejects, still starts and records every action as a receipt gap. The
  plain-http check resolves a host name at load time; a name that resolves differently later is
  caught only by the connect-time guard. Undeclared actions in
  non-strict posture, reversible declarations, and deployments with Averin
  disabled still have no record-existence guarantee (with Averin disabled there is no
  receipt to fail, so no gap event either). That split is the intended
  posture, not an oversight. While Averin cannot begin two-phase evidence, which
  actions are refused is the operator setting `[averin] d8_evidence_floor`
  (CONFIGURATION). In the default `money_and_irreversible` mode, money (an action in
  the `money.*` namespace, or one the catalog declares irreversible) and irreversible
  actions are refused, including a partially-reversible money action such as
  `money.notify`; other partially-reversible actions (in the Solo pack most write
  actions such as session create, update and cancel, attendance update and learner
  messages) and reversible actions keep running. In `human_floor` mode every
  partially-reversible action is refused as well and only reversible non-money
  actions keep running. Actions with no catalog declaration are refused in both
  modes. The setting has an effect only with `d8_complete_evidence = true`. With
  `d8_complete_evidence = true` (the FeirOS Solo setting) an action that may run gets
  two-phase evidence while Averin is up. Only when Averin is
  unavailable (unreachable, timed out, a 5xx or a 429) does it still run, with a
  one-phase seal, an `AVERIN-D8-DEGRADED` alarm line and a `d8_degraded` counter
  (`averin_seal` in `/api/v1/metrics`); that seal can be dropped or lost in a crash,
  and the plan 085 reconciliation detects the gap, it cannot recover it. In the
  default mode a degraded partially-reversible write therefore has no before-act
  record: that is the accepted trade of running routine writes through an Averin
  outage, and `human_floor` is the setting that closes it. Any other
  evidence failure refuses, as it does for every other class: a 4xx from a live
  Averin, a malformed reply, and params over `max_seal_params_bytes` (checked
  before the use token is spent). An action with no catalog declaration is not
  proven reversible, so with `d8_complete_evidence` on it is refused while Averin
  is down in both modes. Whether an operator declared the real side effect
  truthfully is not checked, so the default mode's money line is only as good as the
  catalog's `reversibility` and the `money.*` naming.

- **The outbox is capped, and the cap drops events a consumer may not have read.**
  `[outbox] max_retained_events` (default 2000) bounds the retained events because every outbox
  operation rewrites the whole file, so its cost is O(retained), bounded by the cap but not constant.
  The GC tick prunes the oldest events beyond the cap whatever their delivery state (never past a
  staged intent). A consumer that is down for longer than the cap window loses the events it had
  not read, and sees a hole in the signed sequences (and in the `oldest_sequence` hint); detecting
  it and acting on it is the consumer's job. Vultrino cannot tell whether a poller read an event:
  in push mode `Delivered` means govder acked it, not that leria read it, and in poll-only mode
  (`outbox.enabled = false`) nothing is ever `Delivered`. `cap_pruned_undelivered_total` therefore
  counts events the push target had not acked, not unread events, and leria's hole detection is the
  only unread-loss signal. An undelivered approval event pruned this way is lost (counted, not
  recovered). The GC runs once 60 delivery intervals of wall-clock time (about 5 minutes) have
  passed since the last GC, checked after each delivery pass, so a pass stretched by a hung push
  target delays it and the retained count can exceed the cap by more than the steady-state rate
  times 5 minutes. The counters are per process and reset on restart, and the
  hints are unsigned.
- **An `internal_http` capability's HTTP verb is operator authority, and the agent
  may not send one.** The transport requires `method`, so a capability registered
  through the admin API must make it decidable: exactly one `target.methods` entry,
  or an explicit `target.plugin_params.method` pin (govder writes the pin). Neither,
  both-in-disagreement, or two declared methods is refused at registration
  (`POST`/`PUT /capabilities` 400s), because a verb resolved at call time is a verb
  resolved by the agent. A `tools/call` that carries a `method` argument is refused
  before the use token is consumed — not silently overridden, since executing a
  money action the caller did not ask for is its own defect. This is asymmetric with
  the `http` plugin on purpose: there the caller may still supply `method`/`url`
  within the target scope and policy enforces them independently.
- **A capability's `input_schema` is not checked against the plugin it composes
  into.** vultrino surfaces the operator's schema verbatim in `tools/list`; nothing
  in this plane refuses a schema declaring an argument the backing plugin drops
  (`http`) or refuses (`internal_http`, which deserializes with
  `deny_unknown_fields`). The check exists one plane over, in feir-os's
  `orgpack validate` (`capability-schema-uninvokable`), and only for org packs — a
  capability registered by any other client is unchecked.
- **Resume intentionally does not reproduce the observe downgrade.** An
  observe-tenant action that is both policy-denied and approval-gated is enforced
  rather than observed-away when it resumes—a safe over-block, not an authority
  bypass. Credential identity and tenant isolation are revalidated separately:
  the concrete record revision is frozen at open and must still match, and the
  opener must remain authorized for its tenant.

- **Legacy approvals without a credential-revision snapshot cannot execute.**
  They remain readable for diagnosis, but alias equality cannot prove which
  credential a human reviewed. Re-open them against the current credential.

## Non-goals (out of scope for this plane)

- **Pricing, rate-cards, ledgers, budgets, reconciliation** — the metering plane's
  job; Vultrino emits raw observations only.
- **Cryptographic, tamper-evident audit proofs** — a proof-plane concern; Vultrino
  emits an HMAC-signed, ordered event stream for a proof plane to elevate.
- **A control/decision policy author UI** — Vultrino enforces and brokers; the
  decision logic (who may do what, budget verdicts) is authored elsewhere and
  pushed through the admin API.
- **Being the four-plane OS.** Vultrino is the enforce plane, published and usable
  standalone. The combined OS is a separate product; Vultrino exposes only the
  contracts an integrator needs.

## Gateway refusal records (feir-ops#1): what they do not cover

Each refusal of an authenticated agent is sealed by averin as a `gateway-refusal` record (see
CONFIGURATION, `[averin]`). What that does and does not give you:

- **A floor, not a complete count.** Unauthenticated attempts (no bearer, an unknown or malformed
  secret, an invalid API key) are not recorded: there is no agent to attribute them to; they stay in
  `unauthorized_attempts` and the logs. A refusal that happens before the principal is known on the
  MCP surface is recorded only when the presented `api_key` argument resolves to a stored principal.
  A refusal with no principal at all (local CLI use) is not recorded.
- **Not Level 3.** averin never sees the attempt: vultrino reports it and averin seals it. Suppressing
  a refusal before it is noted is undetectable, and the record proves nothing about what the agent
  tried beyond what vultrino reported.
- **Records can be lost.** A refusal is held in memory until the next drain (two seconds) and, when it
  is a coalesced tail, until its window (default 10 seconds) closes. A process killed in that time
  loses what it had not sealed, with no gap record (the `policy.denied` outbox events written at
  refusal time still exist for policy, kill and cross-tenant refusals). A record that averin does not
  accept (unreachable, 5xx or 429 for three drain ticks, or any other error status at once) becomes an
  `evidence.receipt_gap` event with `kind: refusal`, which has the same retention limits as every gap
  event (see the receipt gap note above). The pending buffers are bounded: a record dropped past the
  bound is a gap with reason `refusal_budget_overflow`.
- **Detail is traded for volume.** One record per agent, action, reason class and entry point per
  window, then a token bucket (burst 60, 20 per hour by default); beyond it refusals merge into one
  summary record with exact per-class counts and no per-action detail. The attempt counts stay exact
  while the process lives; the worst case is about 15,000 records a month per deployment.
- **Reason classes are coarse and fixed.** There are 14 (averin's vocabulary, vendored in
  `vectors/refusal-classes.v1.json`). A refusal of a dispatch that needs evidence vultrino cannot
  obtain (averin refused or unreachable for an action that requires committed evidence, an oversize
  evidence body, a permit that did not match, a changed approval recipe) is sealed as
  `decision_unavailable`, because no finer class exists. A rate limit nested under `or` or `not`, and
  the default of a policy, are reported as `policy_deny`; only the top-level Allow tier distinguishes
  `rate_limit` and `spend_cap`. A V6 halt is `kill_fence`.
- **Names come from the agent.** The action (before it is canonicalised) and a tool name are
  agent-supplied. They are kept only when they are a short plain identifier
  (`[A-Za-z0-9._:-]{1,128}`) and do not contain `vk_` or `vut_`; anything else is stored as
  `invalid_name`. A plain identifier is stored verbatim in a permanent record, including one that merely
  looks like a secret to a human. The record never carries params, a URL, a payload or vultrino's
  free-text refusal reason.
- **Anyone with the averin key can forge one.** vultrino and the other planes share one project-scoped
  `AVERIN_API_KEY`; any holder can submit a refusal record to averin, so a refusal record is evidence
  that a key holder reported it, not that vultrino did. A key split is not built.
- **Needs averin's endpoint.** Against an averin without `POST /v2/refusals` every refusal record is
  rejected and becomes a gap. The classes and entry points must stay equal to averin's file; a test
  pins the vendored copy.
- **Not driven here.** The dispatch-time kill-fence refusal and the evidence refusals of the
  approval-resume path are tagged and noted by the same boundary but have no test of their own; the
  entry point x class table drives the admission gate on `execute`, MCP, `/llm` and the approval
  poll, and the buffered and streaming dispatch tails for the evidence refusal. The CI tests use a
  stub averin. One `#[ignore]` test (`tests/refusals_real_averin.rs`) runs a real averin-server built
  from the averin branch, by hand: it is not a CI gate.

## Rate-limit windows are per-process and per-replica (vultrino#6)

RateLimit rule state (the fixed-window counter) is in-memory and per-process: it resets on restart and
does NOT coordinate across HA replicas, so a rate cap of N/window effectively becomes N*(replica count)
across a horizontally-scaled deployment. RateLimit is a coarse abuse/burst guard, NOT a hard financial
ceiling. For a hard global cap either run vultrino single-replica, front it with a shared external
rate limiter, or rely on the per-agent BUDGET (leria/govder, which IS global and durable) as the
authoritative spend boundary. (Item-6 vultrino#10 fixed the separate bug where layered/per-principal
rules shared ONE counter — they are now keyed per (rule, alias, principal); this bound is the
remaining per-replica multiplication, which is inherent to in-process counters.)

## RateLimit policies stored before the default-deny rule

`Policy::validate` refuses a policy with a `RateLimit` condition unless its
`default_action` is deny (config load and admin API). A policy read back from the
vault with that shape is refused when the server loads stored policies
(`VultrinoServer::reload_policies`, the periodic refresh, and the startup load of
`vultrino web` and `vultrino serve --mcp`, which then do not start). The refusal
covers only that shape: a stored policy failing another validation rule (a nested
`SpendCap`, a zero `RateLimit` dimension, a degenerate `TimeWindow`) is still only
logged as a WARNING and enforced as written. The check runs where the server
loads from the vault; the engine's own `add_policy`, `load_policies` and
`load_policies_if_newer` still only warn, so code that feeds the engine directly
is not covered. A process already running when an older binary writes such a
policy keeps its last good set (the refresh refuses the new set as a whole), so a
later valid change in the same vault is not picked up until the refused policy is
fixed. That includes the kill policy `halt_agent` stores: the halt response then
reports `policy_active=false` and a long-running `serve --mcp` process does not apply
it (token revocation still applies) until the refused policy is fixed. The fix, `vultrino policy deny-default <id>`, only tightens the policy.

## URL policy matching: what canonical matching does not cover

`url_match` is evaluated on a canonical form of the URL (see CONFIGURATION.md).
This does not model what an upstream server does with the bytes: a server that
treats an encoded slash or a different case in the path as the same resource as
another spelling is outside it. A trailing dot on the host is removed by
canonicalisation, because it names the same destination in DNS. A glob pattern
(no trailing `*`) is matched part by part against a URL with a host: scheme,
host, port and the rest (path and query), so a wildcard in the scheme or host
stays in that part on every rule polarity. Inside the host it still matches
any run of host characters, dots included: `https://*.example.com/x` also
matches `a.b.example.com`, and `https://api.example.com*/x` matches
`api.example.com.evil.net`. A glob without a port matches only a URL without
one (the default port), so a Deny or Prompt glob such as `https://*/admin`
no longer matches `https://h:8443/admin` and denies less than before; write the
port (`https://*:*/admin`) to cover other ports. A glob without a scheme is read
with any scheme only when it starts with `*` (`*.example.com/x`); any other
glob without a scheme (`ht*.example.com/x`) matches no URL with a host. A
wildcard in the path or query still matches `/` and `?`, and a path-only URL is
matched as one string. These rules are shown on the tested patterns and a
property test over generated other-host URLs, not proved for every pattern. In
a prefix pattern (trailing `*`) an earlier `*` is literal, so
`https://*.example.com/*` matches no real host: a Deny or Prompt rule written
that way is dead. The admin API, the config file and the stored-policy load all
refuse such a pattern (and every other warned pattern, including an exact URL
with no query and a `{a,b}` glob) on a Deny or Prompt rule: the admin API
answers 400, config load is an error, and a stored policy that holds one makes
`vultrino web` refuse to start and the live set stay unchanged, naming the policy
and the fix (`vultrino policy check` lists them, `vultrino policy
fix-url-patterns <id>` rewrites an exact URL to `<url>*` and expands `{a,b}`).
An Allow rule is refused only when the warned pattern sits under an odd
number of `not` (there a dead pattern allows every URL); any other Allow rule is
stored and warned. A Deny or Prompt rule's `url_match` (flipped under each `not`)
also matches the URL with trailing query parameters removed and with one trailing
`/` of the path removed, so `?x=1`, `&x=1` or a trailing `/` appended never slips a
request past a pattern written without them (an Allow rule is not widened, so a rule
that allowed the bare URL no longer allows it with a query). A pattern that itself
holds a `?` (a literal query, a bare trailing `?`, or the glob one-character
wildcard) is refused on those rules, because a parameter inserted before or
between its own would slip past it: write the path and a trailing `*`
(`https://api.example.com/v1/transfer*`); `vultrino policy fix-url-patterns`
rewrites a stored one to that prefix form. The same widening also drops trailing
`/` characters and `;name=value` path parameters (Java servlet containers and Spring
route `/x;jsessionid=1` to `/x`), and reads `%2F` as `/` and collapses repeated `/`
in the path (reverse proxies merge `//v1/refunds` into `/v1/refunds`). The widening of a Prompt rule can only turn
an Allow into a Prompt, never a Deny into one: the exact-URL Prompt that govder compiles
(an and of url and method, default deny) still prompts only on the exact URL, and its
query and trailing-slash variants stay denied, as before. The wide reading of a Prompt
rule does not charge its rate limit (only the exact reading does), so a request that ends
Denied never uses up the slot. Spellings the widening does not cover still slip past a
Deny pattern written without them: any other rewrite a particular backend applies
(case folding of the path, unicode normalisation, backslashes). The refusal is
as good as the warnings: a glob without a port that misses a non-default port is
not refused.
A glob whose host part holds `?`
is not canonicalised (warned); that `?` matches one host character. Patterns
are canonicalised when they are matched, not rewritten in storage, so the admin
API still shows the text the operator wrote. A `UrlToken` credential is judged
on its placeholder URL and sent as that judged string with the secret in place of
the literal `{credential}`. A URL in which other text canonicalises to a
spelling of the placeholder (percent-encoded, half-encoded, or with an escaped
inner letter such as `%7Bcr%65dential%7D`, in any letter case) is refused; this
is tested on a list of spellings, not proved for every URL. A secret that contains `/`, `?`, `#`, `\`, `%`, whitespace or a control
character is refused when the credential is stored and again when it is used,
because it would change the path or query that is sent; other secrets are
inserted as is and the substitution is checked for an unchanged scheme and
host. A `url_match` glob has no `{a,b}` alternation: the braces are literal, so
such a pattern matches nothing (a Deny or Prompt rule written that way is now
refused, see above). A scheme-less prefix such as `internal*`
matches no canonical `http(s)` URL; it logs the star-in-host warning, which is
the only sign that a Deny or Prompt rule on it is dead (`http*` and `https*` do
not warn). The server code that builds the judged URL (at request time and at
approval resume) has no registered mutant; one integration test
(`internal_http_integration::query_is_forwarded_and_is_part_of_the_policy_matched_string`)
exercises the request-time path. Only the
`http` and `hmac` plugins send the canonical string, and so does `internal_http`
(it composes the pinned base with the canonical path and query, and its path
allowlists run on that composed path). The WASM
plugin egress, ssh and postgres plugins do not use the `url` param and are not
covered. The `hmac` plugin appends `timestamp`, `recvWindow` and `signature` to
the evaluated query pairs, sorted among them; those three are not judged. AWS
SigV4 requests re-sort the query pairs for signing. The `query` map is judged
only when it is a JSON object; a value that is not a string is judged as its
JSON text, and the `http` and `hmac` plugins refuse such a map. A prefix that
ends in `*` inside a host (`https://api.*`, `https://10.0.0*`) is matched as
the one host the URL parser reads from it (`api`, `10.0.0.0`) and is warned, so
a deny rule of that shape no longer matches longer host names or other
addresses and denies less than before (the admin API now refuses such a pattern
on Deny and Prompt rules when a policy is written; one already stored still
loads). A
pattern without a trailing `*` (an
exact URL or a glob that ends in a path) must match the query too: a deny rule
on `https://host/admin` does not match `https://host/admin?x=1`, whether the
query is in `url` or in the `query` map. The meaning-change warning compares
the pattern with a loose normal form and is tested on examples only, so it can
miss a change. Deny rules and the unparseable
pre-check run before the kill tier, so a halted principal with an unparseable
URL gets the unparseable reason instead of the halt reason; the outcome is still
Deny.
